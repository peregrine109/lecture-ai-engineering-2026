結果の根拠は [results](results/) 以下の原本JSONと学習ログ。表の値はこれらから集計した。最終lossはstep 40で記録された最後のログ区間の平均であり、全学習期間平均のtrain_loss_meanではない。学習秒数はtraining_secondsであり、推論評価のsecondsとは区別した。

## 宿題

### 取り組んだレベル
基礎・実装の両方。

### 基礎：学習率だけ変更
baselineのlr=2e-4をbasic_lrでは1e-4に変更した。記録されたconfigの差分はlrのみであり、train.jsonl・test.jsonl・gold.jsonはバイト単位で一致した。モデル・学習量・生成条件をそろえた比較である。基盤モデルから各条件を実行し直す手順を用いたが、セッション再起動操作そのものはZIPには記録されていない。

学習後の形式はどちらも21/21、内容は18/21から20/21に改善した。学習時間は227.14秒と225.61秒でほぼ同程度だった。1回ずつの測定のため、約1.5秒の差を学習率による高速化とは解釈しない。

| 条件 | 根拠あり内容正解 | 根拠なし内容正解 |
|---|---:|---:|
| baseline | 15/15 | 3/6 |
| basic_lr | 14/15 | 6/6 |
| implementation | 12/15 | 5/6 |

学習率を下げると、baselineで失敗した根拠なし3問は正解になった一方、「PDF以外でも出せますか」は確認要求になり、不正解となった。つまり正解が一様に増えたのではなく、確認要求の判断に変化があった。

最終lossは0.013786から0.030305に上がったが、評価の内容正解率は上がった。学習データに対する損失と、別の言い回し・未知質問に対する評価成績は必ずしも同じ方向に動かない。過学習の緩和は可能な説明の一つだが、今回の単一seed・各1回・21問の評価だけでは断定できない。

### 実装：架空の経費精算FAQ
実在企業の規程ではない。FAQ、GROUNDED、UNGROUNDEDと評価専用の質問・知識質問を経費精算の題材へ変更した。JSONのanswer（文字列）とneeds_review（真偽値）の設計は維持した。

| 項目 | 架空の規程 |
|---|---|
| 期限 | 利用月の翌月5日 |
| 申請先 | 社内システム「ケイヒ」 |
| 領収書 | PDF形式で添付 |
| 相談時間 | 毎週火曜15:00〜16:00 |
| 期限後 | 上長の承認を得て経理に連絡 |

学習データ14件、検証データ7件、評価21問（根拠あり15・根拠なし6）という設計を維持した。保存されたtrainとtestの質問は重複していない。validはZIPに含まれないため、提出コードで設計を参照できるようにした。

「根拠なし」の質問は、交通費・宿泊費の上限などの未記載事項と、FAQに近いが規定のない例外条件から作った。評価には「締切の5日が祝日なら翌営業日でよいか」「PDFの容量上限」「相談の事前予約」「上長不在時の代理承認者」を含めた。一般的な推測を答えるのではなく、このFAQから判断できるかを試すためである。

形式は5/21から21/21、内容は3/21から17/21に改善した。ただし言い換えに対して根拠ありの3問を確認要求にし、根拠なしの1問を通常のルールで回答する失敗が残った。形式の安定と根拠の判別を別々に評価する重要性を確認した。

implementationは題材・質問が異なるため、baselineとの85.71%対80.95%の比較だけで、経費精算の学習が劣るとはいえない。学習時間の短縮にも系列長や実行環境の揺れが関係しうる。

### ファインチューニングが向く場面・向かない場面
今回の結果では、固定JSON形式や定型的な応答方針を学ばせる用途に効果があった。全条件で評価21問の形式遵守率が100%になった。
一方、FAQの近接項目と未記載の例外条件を区別する判断は保証されなかった。頻繁に改定される規程の正確な管理や、承認権限・例外条件の判断を学習済みモデルだけに任せる用途には不十分である。最新規程の検索、根拠の提示、ルールによる検査、人への確認を組み合わせる設計が必要と考える。

本実験はFAQを毎回プロンプトに与えているため、正答率向上を単に「モデル内部へ新しい知識が保存された」と解釈することはできない。また、内容採点は必須語句とneeds_reviewによるもので、意味的な正しさを完全に測る指標ではない。今後は未見FAQや例外条件を増やし、複数seedで確認する必要がある。
